# "코테에서 맞는 것"과 "설계로 맞는 것"을 구분해서 가르쳐야 한다

## 관찰

사용자가 처음에 ① 원소를 포인터 배열(`Point* queue[]`)로 담고 ② 큐 자체를 구조체로 만들려 했다. **나는 둘을 뭉쳐서 만류했다.** ①은 만류가 맞았지만 ②는 사용자 직감이 옳았고, 제대로 답하지 않았다.

이후 사용자가 "전역변수를 이렇게 많이 써도 되는지"를 스스로 물었다. 즉 **내가 준 관용구를 그대로 받아들이지 않고 설계 타당성을 검증하려는 성향이 있다.**

## 결론

전역변수 방식을 가르칠 때는 **왜 그것이 이 맥락에서 맞는지**를 함께 줘야 한다. 기술적 근거(단순 편의가 아님):

1. **스택 크기** — 지역 배열은 스택(1~8MB)에 잡혀 큰 배열이 불가능. 전역은 BSS. 실증: `int big[3000][3000]`(36MB)을 지역으로 선언하면 즉시 크래시, 전역이면 성공
2. **자동 0 초기화** — 전역/static은 0으로 초기화. `visited`/`dist`에 `memset` 불필요
3. 인자 전달 실수가 없다

전역이 실무에서 나쁜 이유(코테 조건과 정확히 반대):
- 함수 시그니처가 무엇을 건드리는지 말해주지 않음
- **같은 자료구조를 두 개 만들 수 없다** (양방향 BFS, 0-1 BFS에서 실제로 필요)
- 테스트 간 상태 오염, 스레드 비안전

판단 기준: **자료구조가 하나뿐 + 수명이 짧음 + 파일 하나 → 전역. 하나라도 아니면 구조체.**

핵심 연결: **전역변수는 "인자를 없애서" pass-by-value 문제를 피한 것이고, 구조체+포인터는 "복사되지 않게 넘겨서" 해결한 것이다.** 같은 문제의 두 해법 ([[0001-python-to-c-state-handling]]).

## 향후 세션에 주는 함의

- **스택은 구조체+포인터 방식으로 구현**시킨다. 큐(전역)와 대조되고, 포인터 연습이며, 1.5단계 연결 리스트의 준비다. `PLAN.md` 1단계에 반영
- 관용구를 줄 때 "이 맥락에서 맞다"는 경계를 명시할 것. 이 사용자는 경계 없는 규칙을 받으면 스스로 되물으므로, 미리 주는 편이 효율적
- `malloc`의 정당한 용례(불투명 포인터 + 실행 시점 크기 결정)를 1.5단계에서 반드시 다룰 것. 1단계에서 "malloc 대신 정적 배열"만 배운 상태를 방치하면 "malloc은 나쁘다"로 굳는다 ([[0002-coding-test-bias-in-curriculum]])
- 참고 파일: `reference/queue-two-designs.c` — 같은 큐를 두 설계로 구현, 컴파일 가능
