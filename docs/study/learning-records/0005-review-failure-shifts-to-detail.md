# 재현 실패의 성격이 바뀌면 교정 도구도 바뀐다

## 관찰

2178 복습 1회차(9/1). 빈 파일 재작성으로 정답까지 도달했으나 결함 5개가 나왔다. 그런데 **결함의 성격이 8/22~8/23과 완전히 다르다.**

8/22 최초 풀이의 막힘 4건은 전부 **"상태를 누가 소유하는가"** 였다 — 큐를 인자로 넘기려 함, 선언 순서, `pop()` vs `pop()`. 구조적 오해다 ([[0001-python-to-c-state-handling]]).

9/1 복습의 결함 5건은 전부 **세부 정확도**다:
- `int dr = {...}` — `[4]` 누락
- `buf[j] - '0'`에서 `[j]` 누락 (8/23 2667과 **동일 실수 반복**)
- `dist[nr][nc] != -1` — 부호 반대
- `nc < MAX_N` — 경계 변수 오류
- `printf` 누락

구조는 굳었다. `push(const int r, const int c)`를 처음부터 올바르게 썼고, 크기 상한 `MAX_N * MAX_N`도, 선언 순서도, `pop()` 후 `cur.r`로 이웃 계산도 맞췄다. **8/22의 병목 4개 중 4개가 해소되었다.**

## 결론

**"C 관용구를 제시한다"는 교정 도구는 임무를 마쳤다.** 이제 남은 실패는 관용구를 모르는 게 아니라, 아는 것을 쓸 때 한 글자·한 부호를 놓치는 유형이다. 이 유형은 설명으로 줄지 않는다 — **작성 직후 스스로 훑는 체크리스트**로 줄어든다.

특히 두 항목은 **반복 실수**로 확인되었다:
1. `buf[j] - '0'` — 2667(8/23), 2178 복습(9/1) 두 번
2. 배열 경계/크기에 상수(`MAX_N`)와 변수(`M`, `N`)를 혼용 — `que[MAX_N]`(8/23), `nc < MAX_N`(9/1)

그리고 **"조용히 실패하는 버그"가 3회 연속 등장**했다: `while (is_empty())`(8/22) → `head`/`tail` 리셋 누락(8/23) → `printf` 누락(9/1). 컴파일 통과·경고 0개·exit 0인데 아무 일도 안 일어나는 유형. C에서 컴파일 성공이 정답의 근거가 아니라는 감각이 아직 습관이 되지 않았다.

## 향후 세션에 주는 함의

- **`reference/` 치트시트를 지금 만든다.** `PLAN.md`는 "스택·힙 구현 후"로 미뤄뒀지만, 근거가 바뀌었다. 관용구 설명서로서가 아니라 **격자 BFS 작성 직후 훑는 체크리스트**로서 필요하다. 항목은 위 반복 실수 목록에서 직접 나온다 — 배열 선언의 `[]`, `buf[j] - '0'`, 방문 검사의 부호, 경계에 쓸 변수, 반환값을 출력하는지
- **복습 판정 기준을 세분화**할 것. "정답에 도달했는가"만 보면 이번은 성공이지만, 논리 버그 2개가 나왔으므로 +7일이 아니라 +3일 리셋이 맞다. 판정은 **결함의 성격**으로 한다: 구조적 결함 = 리셋, 세부 결함만 = 정상 진행, 무결함 = 다음 간격
- 앞으로 격자 BFS 문제(7576 → 2206 → 13913)에서는 구조 설명 시간을 줄이고 **작성 후 체크리스트 검증**에 시간을 배분한다
