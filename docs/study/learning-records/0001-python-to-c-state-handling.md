# Python→C 전환의 첫 병목은 알고리즘이 아니라 "상태 소유권"

## 관찰

BFS 개념 이해는 거의 온전히 남아있었다(거리 순서 전파, 첫 도달이 최단이라는 근거를 스스로 설명함). 반면 **큐를 C로 구현하는 단계에서 4번 막혔고, 4번 모두 알고리즘이 아니라 C의 상태 관리 규칙이었다.**

핵심 오해: `push(Point** que, int head, int tail, ...)` 처럼 큐의 상태를 인자로 넘기려 했다. Python에서 `deque` 객체를 넘기면 메서드가 상태를 바꿔주는 경험이 그대로 전이된 것. C에서는 값이 복사되므로 함수 내 `tail++`이 호출자에게 보이지 않는다.

## 결론

이 사용자에게는 **알고리즘 복습보다 "C로 자료구조를 어떻게 소유·조작하는가"의 관용구를 먼저 굳히는 것이 병목 해소에 효율적이다.** 개념은 살아있으니 개념 강의에 시간을 쓸 필요가 적다.

굳혀야 할 C 관용구:
- 자료구조는 전역 값 배열 + 인덱스 정수. `malloc` 회피 (크기 상한을 알면 정적 배열이 더 빠르고 안전)
- 선언 순서: `#define` → `typedef` → 전역 → 함수. "쓰기 전에 선언" (2회 반복 실수)
- `pop(void)` — `()`는 인자 검사를 끄는 옛 문법

## 향후 세션에 주는 함의

- 새 자료구조(스택/힙/해시맵)를 다룰 때마다 같은 병목이 재현될 것으로 예상. 매번 "전역 값 배열 + 인덱스" 틀을 먼저 제시하면 빠르게 넘어갈 수 있다
- **`reference/` 문서 후보**: "C 코테 자료구조 관용구" 치트시트 — 큐/스택/힙 골격, 선언 순서, 자주 쓰는 printf/scanf 포맷. 큐 외에 2개 정도 더 구현한 뒤 만들면 밀도가 좋을 것
- 조용히 실패하는 버그(`while (is_empty())`처럼 컴파일·실행 모두 통과하고 아무 일도 안 하는 유형)에 대한 경계를 계속 심어줄 것. C에서는 컴파일 성공이 정답의 근거가 되지 않는다는 감각
